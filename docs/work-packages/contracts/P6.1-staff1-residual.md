## 1. Executive Summary & Scope Boundaries

### 1.1 Executive Summary
The STAFF-1 milestone established the baseline data models and algorithmic foundations for employee roster management, recurring schedule series, single-occurrence schedule exceptions, and branch-scoped overlap detection within EvoGym. 

While the core weekly recurrence generator and mathematical cycle bounds are implemented in `api/app/api/staff_schedules.py`, the system contains critical operational, algorithmic, and concurrency residuals that must be inventoried, proven, and bounded before proceeding to live frontend binding (FE09) and occurrence-linked attendance execution (STAFF-2 / P6.2).

This contract formalizes:
1. An exhaustive inventory of the baseline implementation (`StaffRosterProfile`, `StaffScheduleSeries`, `StaffScheduleException`).
2. An analysis of the recurrence generation complexity and the 400-year Gregorian cycle boundary ($146,096$ days).
3. The edge case matrix encompassing overnight shifts, IANA DST fold/gap transitions, and multi-shift days.
4. Concurrency vulnerabilities stemming from SQLite testing limitations versus PostgreSQL production row-level locking (`with_for_update`).
5. The frontend integration gap (FE09) between the mock-based `staffStore.ts`/`StaffAttendanceView.tsx` and the backend schemas.
6. Absolute policy compliance with D-032 (branch roster isolation, zero cross-branch deduplication) and system decoupling from member access (P3 / BK-029).
7. An explicit register of pending P1 transport and principal model dependencies.

### 2.1 Entity Model Specifications

#### `StaffRosterProfile` (`api/app/db/models/staff_roster.py`)
- **Table:** `staff_roster_profiles`
- **Identity:** UUIDv4 primary key (`id`), strictly scoped to `branch_id` (`branches.id`).
- **Natural Key:** Case-insensitive full name unique per branch via `Index("uq_staff_roster_branch_name", "branch_id", text("lower(full_name)"), unique=True)`.
- **Invariants:**
  - `expected_entry_time` and `grace_tolerance_minutes` must be both set or both `NULL` (`ck_staff_roster_schedule_complete`).
  - `grace_tolerance_minutes` restricted to `0 <= tolerance <= 1440` minutes (`ck_staff_roster_tolerance_range`).
  - Whitespace-trimmed text validation for `full_name` (max 160 chars) and `position` (max 80 chars).
- **Architectural Reality:** A roster profile is **not** an application user account. Staff members without login credentials (trainers, maintenance personnel) are first-class profiles.

#### `StaffScheduleSeries` (`api/app/db/models/staff_schedules.py`)
- **Table:** `staff_schedule_series`
- **Identity:** UUIDv4 primary key (`id`).
- **Foreign Keys:**
  - `(profile_id, branch_id)` references `staff_roster_profiles(id, branch_id)` with `ondelete="RESTRICT"`.
  - `created_by` references `staff_users.id`.
- **Recurrence Fields:**
  - `start_date`: Date where recurrence begins.
  - `weekdays`: JSON array of integers (`0` = Monday, `6` = Sunday). Constraint `json_array_length(weekdays) > 0`.
  - `start_time`, `end_time`: Naive `Time()` representing local wall-clock time in the branch timezone.
  - `end_date`: Optional terminal date.
  - `occurrence_count`: Optional terminal count (`> 0`).
  - Constraint `ck_staff_schedule_one_termination`: Mutually exclusive termination (`NOT (end_date IS NOT NULL AND occurrence_count IS NOT NULL)`).
  - `cancelled_from`: Optional date marking effective cutoff for future occurrences without altering historical occurrences.
  - `timezone_rules_digest`: SHA-256 hex digest (64 chars) of the IANA TZif compiled binary rules at creation time.

#### `StaffScheduleException` (`api/app/db/models/staff_schedules.py`)
- **Table:** `staff_schedule_exceptions`
- **Uniqueness:** `UniqueConstraint("series_id", "local_date", name="uq_staff_schedule_exception_occurrence")`.
- **Actions:**
  - `'skip'`: Cancels the occurrence on `local_date`. `override_start_time` and `override_end_time` must be `NULL`.
  - `'override'`: Modifies times for `local_date`. Both `override_start_time` and `override_end_time` are required.
- **Audit:** Stores `original_start_time`, `original_end_time`, `recorded_by`, and `recorded_at` (UTC).

#### Gregorian Representative Cycle Proof ($146,096$ Days)
The Gregorian calendar repeats its weekday-to-calendar alignment exactly every 400 years:
$$\text{Span} = 400 \times 365 + 97 \text{ leap days} = 146,096 \text{ days} = 20,871 \text{ weeks (exact integer)}$$
In `staff_schedules.py`:
- `MAX_SCHEDULE_SPAN_DAYS = 146096`.
- For infinite series (`end_date IS NULL` and `occurrence_count IS NULL`), the validation horizon spans exactly `series.start_date + timedelta(days=146096)`.
- If an indefinite series starts within $146,096$ days of `date.max` (`9999-12-31`), it is rejected with HTTP 422 because the full representative proof cycle cannot be evaluated.

#### Overlap Detection Architecture (`_overlaps`)
- Scans sorted UTC intervals derived from local wall times converted via the branch's IANA timezone.
- Pairwise comparisons between two series $A$ and $B$:
  - Two intervals $[A_{\text{start}}, A_{\text{end}})$ and $[B_{\text{start}}, B_{\text{end}})$ overlap if and only if:
    $$A_{\text{start}} < B_{\text{end}} \quad \land \quad B_{\text{start}} < A_{\text{end}}$$
- Exceptions are evaluated outside the representative 400-year cycle by checking a 2-day adjacent window around each exception date (`window_start = day - 2`, `window_end = day + 2`) to catch overnight shifts crossing boundaries.

#### Timezone Digest Validation (`_load_zone`, `_revalidate_profile_timezone_rules`)
- Bypasses Python `ZoneInfo` in-memory caching by directly reading the underlying OS TZif file from `TZPATH` or `tzdata`.
- Computes SHA-256 digest of the raw compiled file.
- If an OS update changes the timezone definition (e.g. government abolishes or introduces daylight saving time), `_revalidate_profile_timezone_rules` catches the digest mismatch, re-evaluates all series wall times, detects any newly introduced overlaps, and updates the digest.

## 3. Residual Gaps Breakdown

### 3.1 Performance & Query Bounds (E02 Gap)

```
[Client Request: Create/Edit Series]
               │
               ▼
┌──────────────────────────────┐
│ Fetch all Profile Series     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ For each existing series:    │
│ Expand 400 years of dates    │ ◄── O(S * W * 20,871) in-memory loop
│ (~20,871 occurrences/series) │     High CPU & GC pressure
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ Convert wall -> UTC & Sort   │ ◄── Python generator converted to list
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ Sweep-line interval compare  │
└──────────────────────────────┘
```

1. **Computational Complexity:**
   - For an employee with $S$ active series and $W$ scheduled weekdays, evaluating an indefinite series across $146,096$ days generates up to $20,871 \times W$ intervals per series.
   - For $S = 5$ series with 5 days each, the overlap sweep parses $\approx 500,000$ intervals in pure Python.
   - While mathematically rigorous for proof completeness, running a 400-year cycle expansion on every POST/PUT request introduces an HTTP request latency bound risk.
2. **Exception Query Scaling:**
   - `_intervals` executes:
     ```python
     select(StaffScheduleException).where(
         StaffScheduleException.series_id == series.id,
         StaffScheduleException.local_date >= first,
         StaffScheduleException.local_date <= last,
     )
     ```
   - On an indefinite series where `last = first + 146096`, this query performs a broad index scan loading all exceptions across the lifetime of the series.
3. **Architectural Recommendation for P6.3 / Production:**
   - Maintain the 400-year proof for recurrence mathematical validation during unit test verification.
   - For runtime API validation, bound the live overlap sweep horizon to an operational window (e.g., $\max(\text{start\_date} + 730 \text{ days}, \text{latest finite series termination})$) combined with recurrence pattern modular intersection tests (checking weekday set intersection and daily time overlap).

### 3.2 Edge Case Schedule Matrix

| Edge Case | Description & Mechanism | Observed Baseline Behavior | Gap / Required Proof |
|---|---|---|---|
| **Overnight Shift Crossing Midnight** | Shift starts at 22:00 and ends at 06:00 next day (`end_time <= start_time`). | `_end_day` increments local date by $+1$ day (`day + timedelta(days=1)`). Interval becomes $[D\text{ 22:00 UTC}, D+1\text{ 06:00 UTC})$. | Sunday overnight shift ending Monday 06:00 correctly conflicts with Monday shift starting at 05:30. Handled in baseline sweep line with 1-day padding. |
| **DST Gap (Spring Forward)** | 1 hour skipped (e.g., 02:00:00 becomes 03:00:00). Local time 02:30 does not exist. | `_local_datetime` round-trips UTC conversion. Fails with `ValueError("The local schedule time does not exist...")` resulting in HTTP 422. | Verified in API. Rejection is strictly conformant with IANA wall-time integrity. |
| **DST Fold (Fall Back)** | 1 hour repeated (e.g., 01:00:00 to 01:59:59 occurs twice). Wall time is ambiguous. | `_local_datetime` explicitly fixes `fold=0` (first occurrence of the repeated hour). | Documented limitation: Does not permit specifying `fold=1`. Accepted trade-off for deterministic weekly schedules. |
| **Multi-Shift per Day (Same Profile)** | Profile works morning shift (08:00–12:00) and evening shift (16:00–20:00) on the same date. | `_overlaps` validates non-overlapping intervals cleanly. | **Sunday-to-Monday Multi-Series Boundary** | Series 1 runs Mon–Fri; Series 2 runs Sat–Sun overnight ending Mon 07:00. | Start date comparison uses $first - 1$ day padding (`first -= timedelta(days=1)`). | Correctly catches the Monday morning overlap from the Sunday overnight shift. |

### 3.3 Concurrency & Database Proof Gaps (P11 Gated)

1. **SQLite Concurrency Illusion vs PostgreSQL:**
   - In SQLite test harnesses, table-level locking obscures race conditions during concurrent schedule modifications.
   - In production PostgreSQL, concurrent transactions modifying or inserting schedule series for the same `profile_id` must serialize.
   - `_lock_profile` executes:
     ```python
     session.scalar(select(StaffRosterProfile).where(StaffRosterProfile.id == profile_id).with_for_update())
     ```
   - **Gap:** In SQLite, `with_for_update()` is silently ignored or converted into a no-op. Full concurrency proof verifying that two concurrent transactions inserting overlapping series are properly serialized (one succeeds, one receives HTTP 409) requires an explicit disposable PostgreSQL container test (gated on P11).
2. **Concurrent Exception Insertions:**
   - Two admins simultaneously submitting exceptions for different dates on the same series:
     - Thread 1: POST override for 2026-11-01.
     - Thread 2: POST override for 2026-11-08.
   - If `_lock_profile` is acquired, these serialize. However, single-occurrence exception edits (`PUT /series/{id}/occurrences/{date}`) must also lock the parent `StaffRosterProfile` row to prevent concurrent creation of an overlapping series on the same profile.

### 3.5 Policy Compliance & Invariants

#### D-032 Invariants (Staff Schedules & Attendance)
1. **Branch Profile Independence:**
   - A roster profile belongs strictly to one `branch_id`.
   - Profiles across different branches are completely independent entities.
   - **Explicit Invariant:** There is **NO** global identity merging, cross-branch profile linking, or cross-branch schedule overlap checking. If "Carlos Perez" works at Branch A and Branch B, he has two separate roster profiles with separate independent schedules. Overlap validation occurs strictly within the same branch roster profile (`ix_staff_schedule_profile_branch`).
2. **Past History Immutability:**
   - Modifying a schedule series via `this_and_future` sets `cancelled_from = effective_date` on the old series and creates a new series starting at `effective_date`.
   - Historical occurrences, exceptions, and past attendance records remain strictly immutable.

#### Decoupling from Member Entry (P3 / BK-029)
- **Architectural Policy:** Staff presence is **NEVER** a technical or logical prerequisite for member facility entry.
- The member access evaluation engine (`evaluate_membership_access` in `api/app/api/membership_access.py` / BK-027 / D-031) evaluates access strictly on membership period validity, branch scoping, payment settlement, and explicit admin restrictions.
- An absent or tardy receptionist does not cause the access control system to reject member entry. The system must operate under kiosk self-check-in or offline mode without staff dependencies.

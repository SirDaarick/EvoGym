# P2.1 — Member Read Contract Inventory & Gap Analysis

Executive evaluation of existing member and sales DTOs against the reloadable read requirements for frontend feature FE05, mapping organization versus branch scope (D-001) and role projection boundaries (D-012).

---

## Quick Summary

| Topic | Decision / Current Reality |
|---|---|
| **Primary Gap (FE05)** | Current member endpoints (`/api/v1/members`) return shallow demographic summaries and aggregate balances without stable IDs for membership periods, class samples, itemized debts, or check-in visits. |
| **Mutation Leakage** | Frontend currently relies on ephemeral checkout responses (`CashMembershipSaleDTO`) to learn period and order identifiers, making browser refresh and bookmarking impossible without losing operational state. |
| **Scope Separation (D-001)** | Member profile identity is organization-shared; financial transactions, cash drawers, shifts, and attendance check-in visits are strictly branch-scoped. |
| **Field Projection (D-012)** | Receptionist role receives only operational member profile, status, and debt warning flags; administrative financial details, audit trails, and staff notes are strictly excluded server-side. |
| **P1 Dependency Gate** | Session principals, standard transport wrappers, and authentication claims are `PENDING P1`; this inventory documents existing models without inventing transport envelopes. |

## 2. Identified Functional Gaps (FE05)

Analysis of `docs/backend-audit/frontend-contract-gaps.md` (item FE05) and current runtime implementations reveals four structural deficiencies:

### 2.1 Lack of Stable Identifiers for Entitlements & Periods
- **Current Defect:** The frontend's `LiveMemberLookup.tsx` receives `OperationalMemberDetail` containing only an aggregate `pending_balance_minor` and boolean `has_pending_balance`.
- **Failure Scenario:** When a receptionist opens a member card to check eligibility or perform check-in (`/api/v1/member-check-ins`), the check-in endpoint requires `period_id: UUID` (or `entitlement_id: UUID` for single-entry class samples). Because no read endpoint provides these IDs, the UI must guess, fabricate IDs, or fail check-in.
- **Contract Requirement:** Member read responses must include an array of `active_periods` and `active_samples`, each with its immutable server-assigned UUID.

### 2.2 Unsafe Dependency on Ephemeral Mutation Responses
- **Current Defect:** Only `POST /api/v1/sales/cash/membership` returns `MembershipPeriodDTO` and `ClassSampleEntitlementDTO`.
- **Failure Scenario:** A receptionist completes a sale, then reloads the page or navigates away. Upon returning, the period and sample IDs vanish because the read endpoints do not project them. The operator cannot review what was sold or check in the member.
- **Contract Requirement:** All member-level reads must be idempotent, reloadable queries backed by database projection (`membership_periods`, `class_sample_entitlements`), completely decoupled from POS checkout transactions.

### 2.3 Absence of Itemized Debt Breakdown for Cash Repayments (BK026-S2 / FE06)
- **Current Defect:** `MemberDetailDTO` exposes `pending_balance_minor: int`.
- **Failure Scenario:** When collecting an outstanding cash repayment (`POST /api/v1/sales/membership-debts/payments`), the request requires `order_id: UUID` (or `debt_id: UUID`). A single balance number cannot tell the receptionist which order originated the debt, when it occurred, or what remaining balance belongs to each order.
- **Contract Requirement:** Administrative and debt-resolution views must provide an itemized collection of open debts: `{ debt_id, order_id, initial_amount_minor, remaining_balance_minor, created_at, order_branch_id }`.

### 2.4 Lack of Reloadable Check-In and Visit History
- **Current Defect:** `attendance_visits` and `member_check_ins` tables exist in SQLAlchemy models (`app.db.models.member_check_ins`), but no read route projects recent check-in events to the member screen.
- **Failure Scenario:** Receptionists cannot verify whether a member already checked in today at the current branch, leading to uncertainty when members tap or present themselves multiple times.
- **Contract Requirement:** Bounded pagination of recent check-in events scoped to the querying branch, returning timestamps, access reason, and access warnings.

## 3. Role Visibility Analysis under Decision D-012

Decision **D-012** mandates strict role-based data projection at the API boundary. Internal ORM objects must never be serialized directly.

```
                              [ Incoming Member Read Request ]
                                             |
                         +-------------------+-------------------+
                         |                                       |
                 Role: Receptionist                         Role: Admin
                         |                                       |
           +-------------+-------------+           +-------------+-------------+
           | Profile: Name, Member #,  |           | Full Operational Profile  |
           | Phone, Photo, Status,     |           | + Itemized Debts & Orders |
           | Emergency Contact         |           | + Administrative Audit    |
           |                           |           | + Staff Notes & History   |
           | Active Entitlements:      |           | + Payment References      |
           | Valid interval, Plan name |           |                           |
           |                           |           | (D-020 sensitive items    |
           | Balance Flag:             |           |  require explicit policy) |
           | Boolean warning ONLY      |           +---------------------------+
           | (No centavos, no orders)  |
           +---------------------------+
```

| Domain Field / Section | Receptionist Scope | Admin Scope | Security & Privacy Rationale |
|---|---|---|---|
| **Member Identity** (`id`, `member_number`, `full_name`, `preferred_name`) | ✅ Visible | ✅ Visible | Essential for front-desk operational recognition and greeting. |
| **Contact Data** (`phone`, `emergency_contact_name`, `emergency_contact_phone`) | ✅ Visible | ✅ Visible | Necessary for operational communication and medical emergency safety. |
| **Personal Demographics** (`email`, `birth_date`, `photo_url`) | ✅ Operational (`photo_url`, `birth_date`) | ✅ Full | Photo enables visual identity check; birth date verifies age bracket/eligibility. |
| **Membership Status & Dates** (`status`, `starts_on`, `ends_on`, `plan_name`) | ✅ Visible | ✅ Visible | Needed to confirm gym floor access rights and answer member renewal inquiries. |
| **Outstanding Balance Warning** (`has_pending_balance`) | ✅ Boolean flag only | ✅ Boolean flag | Notifies receptionist to politely request payment at desk per D-013 / R-007. |
| **Exact Debt Amounts** (`pending_balance_minor`, `initial_outstanding_minor`) | ❌ Hidden (omitted or 0) | ✅ Visible (`bigint` minor) | Receptionists must not view granular financial ledger values without cashier permissions. |
| **Itemized Orders & Debts** (`debts: list[DebtSummary]`) | ❌ Hidden (empty / omitted) | ✅ Visible with order UUIDs | Order IDs, prices, and line items are administrative finance data. |
| **Staff Member Notes** (`notes: list[MemberNoteDTO]`) | ❌ Hidden by default | ✅ Visible (un-voided) | Internal staff notes may contain sensitive behavioral or financial remarks (gated by D-020). |
| **Eligibility Attestations** (`eligibility: list[...]`) | ✅ Current valid type only | ✅ Full history + files | Receptionist only needs to know if student/senior rate is valid today. |
| **Branch Visit History** (`visits: list[...]`) | ✅ Current branch visits only | ✅ Current branch visits | Member movement patterns are branch-isolated; other branch visits are hidden. |

## 4. Tenancy and Multi-Branch Scoping under Decision D-001

Decision **D-001** defines a single-organization, multi-branch model. The read contract must enforce the boundary between organization-shared profiles and branch-isolated transactional records.

| Scope Layer | Domain Entities | Visibility Behavior | Security & Cross-Branch Rule |
|---|---|---|---|
| **Organization Level** (Shared across all branches) | `members`, `plans`, `services`, `plan_versions`, `membership_entitlements` (where `branch_id IS NULL`) | Visible across all branches within the organization. A member registered at Branch A can be looked up at Branch B. | **Lookup Permitted:** Querying `/api/v1/members/{id}` from Branch B returns the member profile and multi-branch entitlements. Cross-organization lookup is strictly prohibited (404/Safe Denial). |
| **Branch Isolated** (Strictly partitioned by `branch_id`) | `orders`, `payments`, `membership_debts`, `shifts`, `cash_registers`, `attendance_visits`, `member_check_ins` | Scoped strictly to the authenticated actor's active `branch_id`. | **Cross-Branch Isolation:** When querying at Branch B, visits and cash debt repayments belonging strictly to Branch A must **never** appear in the response payload. |
| **Hybrid Entitlement** (`membership_entitlements.branch_id`) | Active Membership Period / Entitlement | Conditional access evaluation. | If `branch_id == NULL`, the entitlement is valid at all branches. If `branch_id == 'uuid-branch-A'`, an actor at Branch B sees the entitlement status as `branch_restricted` for local check-in. |

## 5. Dependency Mapping & Pending P1 Gates

Contract design for P2 must interface cleanly with the incoming P1 identity and transport specification (`P1-identity-and-transport.md`). All P1 artifacts are designated `PENDING P1` and must not be simulated or stubbed with dummy auth tokens.

| P1 Interface Point | Current State in Baseline | Required Contract Mapping in P2 | Integration Gate |
|---|---|---|---|
| **Session Principal** | `MemberActorPrincipal(staff_id, is_admin, branch_id)` in `api/app/api/members.py` | Must map to unified `RequestPrincipal` with verified role claims (`admin` vs `receptionist`) and active `branch_id`. | `PENDING P1` — P2 must use abstract dependency injection without asserting token format. |
| **Standard Transport Envelope** | Bare JSON responses in `api/app/api/members.py`; mixed error formats | Read contract defines payload shape; wrapper envelope (e.g. `data`, `meta`, `request_id`) deferred to P1 transport. | `PENDING P1` — P2 specifies inner DTO; client accepts unwrapped DTO until P1 finalization. |
| **Typed Error Responses** | Generic FastAPI `HTTPException(status_code, detail=str)` | Typed domain errors with stable codes (`MEMBER_NOT_FOUND`, `BRANCH_ACCESS_DENIED`, `UNAUTHORIZED_ROLE`). | `PENDING P1` (B05/B06 alignment). |
| **Request Correlation** | Ad-hoc `request_id` in observability logging | Read endpoints must echo incoming `X-Request-ID` or correlate in diagnostic headers. | `PENDING P1`. |

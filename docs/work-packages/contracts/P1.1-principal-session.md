## Decision summary

Treat identity as server-validated authority, not a client-selected role. A resolved principal identifies a staff actor and the scope of the validated credential; every protected operation independently checks the required permission against current staff, branch, and grant state. Branch selection is context, never authority. Organization-wide member-profile visibility follows the approved D-001/D-012 policy; branch transactions, cash, stock, visits, and other branch records/actions require branch-specific authorization.

## Proposed principal/session contract

### Resolved principal

A successful authentication resolution should expose these server-derived fields (exact wire/schema names remain an implementation decision):

| Field | Meaning | Rule |
|---|---|---|
| `actor_id` | Stable staff identity | Derived from the validated session; never accepted from request payload as authority. |
| `credential_kind` | Staff operational session or Admin session | Distinguishes authentication context, not a substitute for permission checks. |
| `session_id` | Opaque internal session identity | Useful for audit/revocation correlation; do not expose unless a consumer need and privacy review justify it. |
| `organization_id` | Organization owning the active grant/resource context | Must be resolved from persisted relationships; do not infer from a selected branch or client claim. |
| `scope_kind` | `organization` or `branch` | Describes the credential/grant scope; branch scope must include its branch identifier. |
| `branch_id` | Bound branch, or null for organization-scoped identity | A null branch does not imply unrestricted access; each operation still requires explicit authorization. |
| `permissions` | None required in the principal by this contract | Evaluate the requested action against current grants on each protected operation; avoid stale cached permission snapshots. |

The existing `SessionPrincipal` is narrower than this proposed normalized contract. Do not silently claim these fields are implemented. The adapter may derive additional fields only from trusted persisted state and an approved design.

### Organization and branch scope

1. Organization-wide profile reads may be shared only within the organization and only to the extent approved by D-001/D-012; D-012 distinguishes receptionist operational profile fields from Admin financial, compensation, and audit access.
2. Branch transactions, history, visits, cash, stock, attendance, and mutations are branch-scoped unless an explicit business decision says otherwise.
3. A branch ID supplied in a URL, body, query, or UI selector is a requested resource context, not a grant. The server must compare it to the validated session and active grants.
4. Organization scope is not blanket permission: role/action restrictions still apply. Branch scope cannot be widened by changing client state.
5. Cross-organization lookup and existence disclosure are denied. The exact uniform 403/404 policy belongs to endpoint/error contract review and is unresolved here.

### Authorization and revocation

- Resolve bearer credentials on each protected request; reject absent, malformed, unknown, inactive, expired, or revoked sessions.
- Re-read active actor, branch, and grant state when authorizing an operation. A grant or account deactivation must affect the next authorization check; no frontend role/PIN/demo fallback may restore authority.
- A revoked session cannot be revived by retry, refresh, branch reselection, or local cache. Reauthentication creates a new session under the then-current policy.
- Session expiry and refresh behavior must satisfy the approved lifetime policy below; source references describe current behavior only and are not evidence that the policy is implemented.
- Revocation endpoint ownership, self-revoke semantics, and whether session revocation is immediate across replicas are not decided by P1.1.

### Error semantics (principal/session scope only)

Authentication absence or invalidity should fail closed and must not reveal whether a staff account, session, grant, organization, or branch exists. Authorization failure must not change the actor's role or leak protected resource existence. Infrastructure unavailability must remain distinguishable from invalid credentials internally while returning only the approved safe API response. Exact status/code/body and frontend handling are P1.3, not decided here. Never log bearer tokens, PINs, recovery codes, or unnecessary PII.

## Approved policy inputs for the proposed contract

The following are user-approved P1.1 policy decisions from the coordinator-provided product-policy instructions (2026-10-23), not claims about current implementation. The file-and-line citations above support only the verified-existing section; existing code must be assessed against these decisions in a separately authorized implementation task.

| Policy area | Contract requirement |
|---|---|
| Admin identity and roles | Every Admin has an individual account. A single owner has all permissions and is the only actor who can grant or remove Admin access. The owner creates reusable role bundles for other Admins; multiple assigned roles combine. The owner may also take Reception duties. |
| First owner / signup | Provision the first owner through a one-time owner/delegate bootstrap. There is no public signup. |
| Admin device/session limits | Allow at most one active Admin computer session and one active Admin phone session. A new or unrecognized device requires email confirmation before its session is created; a trusted device skips repeat approval. Pending approval is single-use, bound to that attempt, expires after 30 minutes, and a newer attempt in the same category supersedes it. Only after approval may a replacement session supersede the prior session in that category; send a security notice. |
| Admin trusted device | Trust remains until an Admin revokes it or account recovery resets trust. Remembered-device inactivity is limited to 30 days, with a 90-day absolute limit. |
| Admin access and refresh tokens | Admin access JWT lifetime is 15 minutes with silent refresh; rotate the refresh token on every refresh. Refresh-token reuse revokes only the affected device session and is logged without email. |
| Admin recovery | Use a registered-email, one-time recovery link expiring after 30 minutes. Responses must not disclose account existence. A successful password reset revokes all Admin sessions and resets trusted-device state. |
| Employee PIN format and lifecycle | Employee PINs are random six-digit values. On activation/reactivation or Admin reset, the Admin sees the initial PIN once and hands it to the employee manually. It expires unused after seven days and must be changed on first use. After expiry, only an Admin may reissue it. A lost PIN is reset by an Admin; reset invalidates the old PIN and active phone and Reception sessions. |
| Employee phone and Reception lifetimes | Employee phone sessions silently renew, with 30 days inactivity and a 90-day absolute limit. Reception sessions have no idle cutoff and a 90-day absolute limit. |
| Employee profile PIN | Request the employee PIN every time an employee profile is opened. Count five consecutive failures for that employee across all devices and Reception; lock only that employee profile for five minutes. At expiry, reset the failure counter to zero. |
| PIN failure alert | Create an in-app alert visible only to Admins with employee-management permission. Keep it until an eligible Admin marks it reviewed; that acknowledgement is global, not per Admin/device. Do not send email for this alert. |
| Activation and PIN reset | Re-activation and Admin reset issue a random six-digit initial PIN. The Admin sees it once and hands it to the employee manually. It expires if unused after seven days and must be changed by the employee on first use. After expiry, only an Admin may reissue it. A lost PIN is reset by an Admin. |
| Reset side effects | Resetting the PIN invalidates the old PIN and revokes the employee's active phone session and Reception sessions. |
| Phone pairing | Each employee may have at most one phone. A fresh Admin-authorized pairing code links a replacement atomically with replacement of the old phone/session; record the event in security logs without creating an alert. Lost phones are unlinked by an Admin, and replacement requires a new pairing. |
| Deactivation | Deactivation revokes the employee's sessions and devices and invalidates pending pairing codes. |
| Security logs | Logs are developer-only and retained for 90 days. Record event, time, employee/device, and initiating actor. Never record PINs, pairing codes, or tokens. |
| Refresh-token reuse | For Admin refresh tokens, reuse revokes only the affected device session and is logged without email. |

These decisions settle the stated Admin and employee session lifetimes and workflows. They do not settle implementation details such as refresh-token storage and atomic rotation/reuse detection, cross-replica revocation consistency targets, log storage/schema and enforcement of developer-only access, or email-provider configuration. The approved registered-email Admin approval/recovery messages do not authorize unrelated email alerts or any provider setup.

## 1. Executive Architecture & Domain Model

### 1.1 Transition Overview
The current attendance implementation (`api/app/db/models/staff_attendance.py` and `api/app/api/staff_attendance.py`) models attendance as a flat daily record per employee:
$$\text{Attendance Identity} = (\text{branch\_id}, \text{profile\_id}, \text{business\_date})$$
This naive structure violates fundamental operational requirements confirmed in **D-032**:
1. **Multi-Shift Prohibition:** It prevents an employee from working multiple shifts in a single day (e.g., a morning reception shift and an evening coaching shift).
2. **Decoupled Tolerance:** It derives expected entry time and tolerance from static profile attributes on `StaffRosterProfile` rather than the active recurring schedule rule or single-occurrence exception.
3. **No Correction Audit:** It lacks an append-only correction entity to record supervisor modifications.
4. **Clock Untrustworthiness:** It relies solely on a single server timestamp, lacking the dual-timestamp schema mandated by **D-033** for offline and distributed operations.

STAFF-2 resolves these gaps by elevating attendance from flat daily records to **Occurrence-Linked Attendance Events**:

```
┌─────────────────────────────────┐       ┌───────────────────────────────────┐
│     StaffScheduleSeries         │       │      StaffScheduleException       │
│  (Weekly recurrence rule)       │       │  (Single-date override / skip)    │
└────────────────┬────────────────┘       └─────────────────┬─────────────────┘
                 │                                          │
                 └────────────────────┬─────────────────────┘
                                      │ generates
                                      ▼
                        ┌───────────────────────────┐
                        │   Scheduled Occurrence    │
                        │ (series_id + local_date)  │
                        └─────────────┬─────────────┘
                                      │ linked to
                                      ▼
                        ┌───────────────────────────┐
                        │   StaffAttendanceRecord   │
                        │ (affirmative check-in)    │
                        └───────┬───────────┬───────┘
          records exit          │           │ receives
     ┌──────────────────────────┘           └──────────────────────────┐
     ▼                                                                 ▼
┌───────────────────────────┐                       ┌──────────────────────────────────┐
│  StaffAttendanceCheckout  │                       │    StaffAttendanceCorrection     │
│   (immutable check-out)   │                       │    (append-only audit trail)     │
└───────────────────────────┘                       └──────────────────────────────────┘
```

## 2. Occurrence Identity & Multi-Shift Architecture

### 2.1 The Scheduled Occurrence Concept
A scheduled occurrence is an ephemeral or materialized work expectation defined by:
1. `series_id`: Foreign key referencing the active `StaffScheduleSeries`.
2. `occurrence_date`: The specific calendar date (`date`) in the branch's local timezone.
3. `scheduled_start_time` / `scheduled_end_time`: Local wall-clock times derived from the series or overridden by a `StaffScheduleException`.

### 2.2 Migration & Resolution of `uq_staff_attendance_branch_profile_date`

#### Existing Constraint Defect
In baseline `staff_attendance.py`:
```python
UniqueConstraint("branch_id", "profile_id", "business_date", name="uq_staff_attendance_branch_profile_date")
```
This constraint enforces at most **one** attendance record per employee per calendar day. If a staff member works 08:00–12:00 and 16:00–20:00 on the same date, inserting the second shift fails with an `IntegrityError`.

#### Proposed Schema Resolution
To support multiple shifts per day while maintaining strict double-check-in prevention:
1. **Drop Constraint:** `uq_staff_attendance_branch_profile_date`.
2. **Add Scheduled Occurrence Constraint:**
   ```sql
   ALTER TABLE staff_attendance_records
   DROP CONSTRAINT uq_staff_attendance_branch_profile_date;

   ALTER TABLE staff_attendance_records
   ADD CONSTRAINT uq_staff_attendance_series_occurrence
   UNIQUE (branch_id, profile_id, series_id, occurrence_date);
   ```
   *Behavior:* An employee cannot check into the *same* scheduled shift series twice on the same date. However, an employee *can* check into two distinct series occurring on the same date.
3. **Index for Daily Projections:**
   ```sql
   CREATE INDEX ix_staff_attendance_profile_date
   ON staff_attendance_records (branch_id, profile_id, occurrence_date);
   ```

### 2.3 Unscheduled / Ad-Hoc Shifts vs Scheduled Occurrences
Real gym operations frequently require unscheduled shift coverage (e.g., an employee covers for a sick colleague, or works an emergency maintenance shift):

| Dimension | Scheduled Occurrence | Unscheduled / Ad-Hoc Shift |
|---|---|---|
| `series_id` | Valid UUID referencing `staff_schedule_series.id`. | `NULL`. |
| `shift_type` | `'scheduled'` | `'ad_hoc'` |
| Tolerance & Status | Status (`present` / `late`) derived from schedule tolerance boundary. | Defaults to `present` (or `unscheduled`), since no expected baseline was configured. |
| Uniqueness Key | `(branch_id, profile_id, series_id, occurrence_date)` | `(branch_id, profile_id, idempotency_key)` or serial `ad_hoc_seq`. |
| Authorization | Standard Receptionist or Admin clock-in. | Requires Receptionist or Admin confirmation specifying reason. |

## 3. Timestamps & D-033 Clock Integrity

```
[Client Device: Check-In]
  ├── Captured Local Instant: 2026-10-23T08:02:15Z (device_captured_at)
  ├── Monotonic Counter: 14920485 ms (if anchor established)
  └── Idempotency Key: uuidv4()
            │
            │ HTTP POST /api/v1/staff-attendance/check-in
            ▼
[Server Gateway]
  ├── Received Instant: 2026-10-23T08:04:10Z (server_received_at)
  ├── Calculate Skew: |08:04:10 - 08:02:15| = 115 seconds
  │
  ├── Rule Check:
  │     ├── Skew <= 300s (5m)? ──► PASS (clock_status = 'verified')
  │     └── Skew > 300s?      ──► FLAG (clock_status = 'skew_flagged', review_required = true)
  ▼
[Database Persistence]
  └── Store BOTH device_captured_at AND server_received_at
      *NEVER auto-correct or shift timestamps*
```

### 3.1 Dual-Timestamp Storage Schema
To prevent clock spoofing and support offline store-and-forward sync, every attendance record and checkout record stores **two** explicit UTC timestamps:
1. `device_captured_at` (`TIMESTAMPTZ`, UTC): The exact wall-clock instant recorded by the terminal or mobile device at the moment of the physical event.
2. `server_received_at` (`TIMESTAMPTZ`, UTC): The exact wall-clock instant the HTTP payload was received and processed by the FastAPI backend.

### 3.2 Monotonic Origin & Anchor Logic
When a client device synchronizes with the server, it obtains a **Server UTC Anchor**:
$$\text{Anchor} = (T_{\text{server\_utc}}, M_{\text{client\_monotonic}})$$
If a client submits an event citing a valid session anchor:
$$\Delta M = M_{\text{event}} - M_{\text{client\_monotonic}}$$
$$T_{\text{monotonic\_derived}} = T_{\text{server\_utc}} + \Delta M$$
- If the monotonic origin matches, the server compares $T_{\text{monotonic\_derived}}$ against `server_received_at`.
- If no monotonic origin is known (e.g. cold start, browser reload), the system falls back to comparing `device_captured_at` directly against `server_received_at`.

### 3.3 Skew Thresholds and Review Flags
Let $\Delta T = | \text{server\_received\_at} - \text{device\_captured\_at} |$.

1. **Within Tolerance ($\Delta T \le 300\text{ seconds}$ / 5 minutes):**
   - Clock is considered synchronized.
   - `clock_status = 'verified'`.
   - `review_required = false`.
   - Attendance status (`present` vs `late`) is calculated using `device_captured_at` converted to branch local wall time.
2. **Excessive Skew ($\Delta T > 300\text{ seconds}$):**
   - Client clock is untrusted (clock tampering, dead CMOS battery, or stale queue replay).
   - `clock_status = 'skew_flagged'`.
   - `review_required = true`.
   - Status defaults to `review_pending` (or provisional status based on `server_received_at`).
3. **Missing or Incoherent Monotonic Origin:**
   - If the client asserts a monotonic origin that does not exist in the server session cache or has gone backward:
   - `clock_status = 'unverifiable_origin'`.
   - `review_required = true`.

### 3.4 Strict Non-Fabrication Invariant
> [!CAUTION]
> **D-033 Invariant:** The system must **NEVER** auto-correct, adjust, or fabricate timestamps. The raw `device_captured_at` and `server_received_at` must remain immutable. Anomalous events are flagged for administrative review rather than silently mutated.

## 4. Status Transitions and Business Rules

### 4.1 Absence as Default Classification
On any calendar date where an active `StaffScheduleSeries` dictates a shift for a profile:
- Prior to affirmative check-in, the operational projection classifies the occurrence as **`absence`** (or `scheduled_unmarked`).
- There is no persisted "absence record"; absence is derived dynamically:
  $$\text{Status} = \begin{cases} \text{Persisted Record Status} & \text{if record exists} \\ \text{absence} & \text{if occurrence date is past and no record} \\ \text{scheduled} & \text{if occurrence is in the future} \end{cases}$$

### 4.2 Present vs Late Evaluation
When an affirmative check-in event arrives:
1. Determine **Effective Start Time**:
   - If an override exception exists for `(series_id, occurrence_date)`: use `override_start_time`.
   - Else: use `series.start_time`.
2. Determine **Tolerance Boundary**:
   $$\text{Tolerance Minutes} = \text{profile.grace\_tolerance\_minutes} \quad (\text{default } 15 \text{ min if null})$$
   $$\text{Tolerance Boundary} = \text{Effective Start Time} + \text{Tolerance Minutes}$$
3. Evaluate Status:
   - Convert `device_captured_at` to branch local wall time $T_{\text{local}}$.
   - If $T_{\text{local}} \le \text{Tolerance Boundary} \implies \mathbf{present}$.
   - If $T_{\text{local}} > \text{Tolerance Boundary} \implies \mathbf{late}$.

### 4.3 Check-Out Semantics
1. **Actual Timestamp Recorded:**
   - Check-out records `checkout_device_captured_at` and `checkout_server_received_at`.
2. **Missing Check-Out:**
   - If staff leaves without checking out, `checkout_at` remains `NULL`.
   - **Strict Invariant:** Missing check-out is **never inferred or auto-completed**. It remains an open shift.
3. **Early Exit:**
   - If staff checks out before `scheduled_end_time`, the actual timestamp is recorded.
   - Early exit **never mutates or cancels** the existing `present` or `late` status.

## 5. Append-Only Corrections & Audit Trail

Once written, `StaffAttendanceRecord` and `StaffAttendanceCheckout` are physically immutable (enforced by database event listeners or triggers rejecting UPDATE/DELETE).

Any manual correction by an Admin or Receptionist creates an immutable child record in `staff_attendance_corrections`:

```sql
CREATE TABLE staff_attendance_corrections (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    attendance_id UUID NOT NULL REFERENCES staff_attendance_records(id) ON DELETE RESTRICT,
    field_name VARCHAR(32) NOT NULL,
    original_value VARCHAR(128) NOT NULL,
    corrected_value VARCHAR(128) NOT NULL,
    reason TEXT NOT NULL,
    corrected_by UUID NOT NULL REFERENCES staff_users(id) ON DELETE RESTRICT,
    corrected_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT ck_staff_attendance_correction_field 
        CHECK (field_name IN ('status', 'occurred_at', 'checkout_at', 'tolerance_boundary')),
    CONSTRAINT ck_staff_attendance_correction_reason
        CHECK (length(trim(reason)) >= 5)
);
```

### 5.1 Permission Scopes for Corrections
- **Administrator (`admin`):** Authorized to perform corrections across **all** staff profiles across all branches.
- **Receptionist (`receptionist`):** Authorized to perform corrections **only** for staff profiles belonging to their assigned branch. Attempting to correct a record from another branch returns HTTP 403 / HTTP 404.

## 6. Idempotency & Replay Semantics (R-013, R-022)

Every check-in and check-out request must include an `idempotency_key` (UUIDv4/UUIDv7):

```
                       [Incoming Request with Idempotency-Key: K]
                                          │
                                          ▼
                      ┌───────────────────────────────────────┐
                      │ Lookup Key K in staff_attendance_keys │
                      └───────────────────┬───────────────────┘
                                          │
                        ┌─────────────────┴─────────────────┐
                 Key Exists?                        Key New?
                        │                                   │
              YES       ▼                         NO        ▼
    ┌───────────────────────────┐                 ┌──────────────────────┐
    │ Compare Request Payload   │                 │ Execute Transaction: │
    └─────────────┬─────────────┘                 │ - Insert Attendance  │
                  │                               │ - Store Key + Hash   │
        ┌─────────┴─────────┐                     │ - Commit             │
     Identical?          Different?               └──────────┬───────────┘
        │                   │                                │
        ▼                   ▼                                ▼
   Return Cached       Reject HTTP 409                 Return HTTP 201
   HTTP 200/201        Conflict                        Created
   (Original Result)   "Idempotency conflict"
```

1. **Exact Replay:** Returns the existing record without side effects.
2. **Conflicting Replay:** Same key with different payload parameters (e.g. different `profile_id` or timestamp) is rejected with HTTP 409 Conflict.

## 7. Offline Conflict and Cancellation Semantics

When a client operates in store-and-forward mode (WAN outage):
1. **Offline Capture:** Reception marks an employee attendance event against a cached schedule series.
2. **Concurrent Central Edit:** While offline, an Admin cancels or overrides that series starting earlier in the week (`cancelled_from <= occurrence_date`).
3. **Reconciliation on Sync:**
   - The server **does not drop** the offline event.
   - The event is persisted into `staff_attendance_records`.
   - `schedule_conflict = true` and `review_required = true` are flagged.
   - An alert is generated for the branch administrator to approve or reclassify the shift.

## 8. Decoupling Invariants

1. **Decoupling from Member Entry:**
   - Member check-in is governed exclusively by `evaluate_membership_access` (P3 / BK-027 / D-031).
   - Staff attendance records are completely decoupled from gym access turnstiles and member check-in portals.
2. **Independent Branch Roster Profiles:**
   - Roster profiles represent physical labor entities in a specific branch.
   - Profiles do not imply user logins and are never linked across branches.

## 10. Data Schemas & API Specifications

### 10.1 SQL Relational Schema (PostgreSQL DDL)

```sql
-- 1. Staff Attendance Records (Affirmative Check-In)
CREATE TABLE staff_attendance_records (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    branch_id UUID NOT NULL REFERENCES branches(id) ON DELETE RESTRICT,
    profile_id UUID NOT NULL,
    series_id UUID NULL REFERENCES staff_schedule_series(id) ON DELETE RESTRICT,
    occurrence_date DATE NOT NULL,
    shift_type VARCHAR(16) NOT NULL DEFAULT 'scheduled',
    
    -- Dual Timestamps (D-033)
    device_captured_at TIMESTAMPTZ NOT NULL,
    server_received_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    
    -- Status & Tolerance
    status VARCHAR(16) NOT NULL, -- 'present', 'late', 'review_pending'
    scheduled_start_time TIME NULL,
    tolerance_minutes INTEGER NULL,
    
    -- Integrity & Audit
    clock_status VARCHAR(24) NOT NULL DEFAULT 'verified', -- 'verified', 'skew_flagged', 'unverifiable_origin'
    review_required BOOLEAN NOT NULL DEFAULT FALSE,
    schedule_conflict BOOLEAN NOT NULL DEFAULT FALSE,
    idempotency_key VARCHAR(64) NOT NULL,
    recorded_by UUID NOT NULL REFERENCES staff_users(id) ON DELETE RESTRICT,
    
    -- Constraints
    CONSTRAINT fk_staff_attendance_profile_branch 
        FOREIGN KEY (profile_id, branch_id) 
        REFERENCES staff_roster_profiles(id, branch_id) ON DELETE RESTRICT,
    CONSTRAINT ck_staff_attendance_shift_type 
        CHECK (shift_type IN ('scheduled', 'ad_hoc')),
    CONSTRAINT ck_staff_attendance_status 
        CHECK (status IN ('present', 'late', 'review_pending')),
    CONSTRAINT ck_staff_attendance_clock_status
        CHECK (clock_status IN ('verified', 'skew_flagged', 'unverifiable_origin')),
    CONSTRAINT uq_staff_attendance_idempotency
        UNIQUE (branch_id, idempotency_key),
    CONSTRAINT uq_staff_attendance_scheduled_shift
        UNIQUE (branch_id, profile_id, series_id, occurrence_date)
);

-- Index for daily roster view
CREATE INDEX ix_staff_attendance_lookup 
ON staff_attendance_records (branch_id, occurrence_date, profile_id);

-- 2. Staff Attendance Checkouts
CREATE TABLE staff_attendance_checkouts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    attendance_id UUID NOT NULL UNIQUE REFERENCES staff_attendance_records(id) ON DELETE RESTRICT,
    device_captured_at TIMESTAMPTZ NOT NULL,
    server_received_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    clock_status VARCHAR(24) NOT NULL DEFAULT 'verified',
    idempotency_key VARCHAR(64) NOT NULL UNIQUE,
    recorded_by UUID NOT NULL REFERENCES staff_users(id) ON DELETE RESTRICT
);

-- 3. Staff Attendance Corrections (Append-Only Audit)
CREATE TABLE staff_attendance_corrections (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    attendance_id UUID NOT NULL REFERENCES staff_attendance_records(id) ON DELETE RESTRICT,
    field_name VARCHAR(32) NOT NULL,
    original_value VARCHAR(128) NOT NULL,
    corrected_value VARCHAR(128) NOT NULL,
    reason TEXT NOT NULL,
    corrected_by UUID NOT NULL REFERENCES staff_users(id) ON DELETE RESTRICT,
    corrected_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT ck_staff_attendance_corr_field 
        CHECK (field_name IN ('status', 'device_captured_at', 'checkout_at')),
    CONSTRAINT ck_staff_attendance_corr_reason 
        CHECK (length(trim(reason)) >= 5)
);
```

### 10.2 Pydantic API DTOs

```python
from datetime import date, datetime, time
from typing import Literal
from uuid import UUID
from pydantic import BaseModel, ConfigDict, Field, field_validator

class StaffCheckInRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    
    series_id: UUID | None = Field(default=None, description="Null for ad-hoc shifts")
    occurrence_date: date
    device_captured_at: datetime
    idempotency_key: str = Field(min_length=16, max_length=64)
    client_monotonic_ms: int | None = None
    note: str | None = Field(default=None, max_length=255)

    @field_validator("device_captured_at")
    def validate_utc(cls, v: datetime) -> datetime:
        if v.tzinfo is None or v.utcoffset() is None:
            raise ValueError("device_captured_at must be an explicit UTC timestamp")
        return v

class StaffCheckOutRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    
    device_captured_at: datetime
    idempotency_key: str = Field(min_length=16, max_length=64)
    client_monotonic_ms: int | None = None

    @field_validator("device_captured_at")
    def validate_utc(cls, v: datetime) -> datetime:
        if v.tzinfo is None or v.utcoffset() is None:
            raise ValueError("device_captured_at must be an explicit UTC timestamp")
        return v

class StaffCorrectionRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    
    field_name: Literal["status", "device_captured_at", "checkout_at"]
    corrected_value: str = Field(min_length=1, max_length=128)
    reason: str = Field(min_length=5, max_length=500)

class StaffAttendanceResponse(BaseModel):
    id: UUID
    branch_id: UUID
    profile_id: UUID
    series_id: UUID | None
    occurrence_date: date
    shift_type: str
    status: str
    device_captured_at: datetime
    server_received_at: datetime
    clock_status: str
    review_required: bool
    schedule_conflict: bool
    checkout_captured_at: datetime | None = None
    checkout_received_at: datetime | None = None
    corrections_count: int = 0
```

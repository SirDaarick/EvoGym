# Implementation Phases and Execution Cards

This is the detailed work plan for BK tasks in the [master ledger](../../odd/tasks/backend-implementation.md). Only the master ledger records status; these cards define scope and acceptance. Dependency decisions can block individual cards without authorizing assumptions.

## Execution method

Deliver one coherent vertical slice at a time. Start with a relevant deterministic failing test when such a runner and clear expected result exist; observe RED, implement the smallest change, observe GREEN, then refactor with tests green. For passive docs, missing runners, or no meaningful deterministic RED, record why and use proportional checks. Do not invent tests/results or make a test framework choice just because one exists in frontend.

For substantial implementation, use one bounded writer with exact edit surfaces and checks. BK-012 is authorized locally; its parent owns the work-unit commit, and the master ledger plus all eight plan documents must accompany every backend commit. Before that commit, normalize and verify; RDD remains user-owned and currently off. No hosted CI, remote service, deployment, or frontend auth changes are authorized by this slice.

### Authorized slice: BK026-S3-A — staff PIN session API

Expose `POST /api/v1/auth/staff/sessions` as a transport adapter over the existing server-enforced `issue_session` service. Expiry comes only from bounded `EVOGYM_STAFF_SESSION_TTL_SECONDS` (60–86400); missing TTL or required auth/session-factory configuration fails closed. Reuse auth rate limiting, bounded hash concurrency, safe generic errors, strict body validation, and body-size protection; send `Cache-Control: no-store`. Keep the existing Admin password session flow and internal service unchanged. No frontend work, provisioning, secrets, deployment, live database, or changes to the master task ledger are included. Verify with isolated SQLite fixtures, focused/full API tests, dependency check, and scoped whitespace checks; PostgreSQL remains opt-in.

### Authorized slice: BK026-S3-B — live reception balance warning

The explicit `/reception/live` route consumes real backend records independently of the DemoProvider experience. Configure the backend HTTP(S) origin and real branch UUID using `VITE_API_BASE_URL` and `VITE_BRANCH_ID`; the route fails closed without valid configuration. Staff authentication uses `POST /api/v1/auth/staff/sessions`, with the returned bearer token limited to tab-scoped session storage. Member lookup uses the authenticated list endpoint and real UUIDs; selecting a member reads detail `pending_balance_minor` and `has_pending_balance`. A positive balance is a visible informational alert and can be refreshed after repayment to clear at zero. Async result generations invalidate stale search/detail responses on new input, selection, logout, and session replacement. Browser access is opt-in through backend `EVOGYM_CORS_ALLOWED_ORIGINS`, a comma-separated exact-origin allowlist; wildcard, credentials, non-origin URL components, and duplicates are rejected. It permits only GET/POST and Authorization/Content-Type, with no credentialed cookies. Tests: focused frontend suite 9 passed; `npm run typecheck` and `npm run build` passed (existing >500 kB chunk warning); focused backend app/auth/session suite 14 passed with one existing Starlette/httpx deprecation warning. No payment collection, check-in enforcement, direct-transfer rules, live database, deployment, or remote service is included.

**Follow-up implementation surfaces:** `frontend/src/features/reception/LiveMemberLookup.tsx` and its tests; `api/app/settings.py`, `api/app/main.py`, `api/tests/test_app.py`, `.env.example`, and API/frontend operator documentation.

#### BK-042-S1 - itemized pending-money read API (Done - 2026-10-21)

A bounded backend-only slice that can ship before broader BK-042 reporting. Return itemized existing source events for pending money; do not calculate or label it as income/revenue. Broader financial reporting remains pending.

**Implemented contract:** `GET /api/v1/admin/pending-money` accepts optional `branch_id` and returns `{items, total_items, total_pending_minor}`. Each item carries `item_type`, branch id/name, member id/number/name, order id, amount/currency, source event id/time, and current status with its latest status-event id/time. Transfer items use Payment as the source and include only `under_review`/`pending`; debt items use the immutable MembershipDebt record as source and calculate `initial_outstanding_minor - sum(append-only receipts)`, omitting fully paid debts. This endpoint is an itemized pending-money view only, never income/revenue. An organization Admin is authorized for each returned branch; a branch-scoped Admin session is constrained to its bound branch, and any requested scope is checked with `FINANCE_READ`.

- **Authorization:** Require authenticated Admin access using the existing Admin financial authorization. If that authorization is absent or ambiguous, stop and record the blocker; do not invent a permission, role, or policy.

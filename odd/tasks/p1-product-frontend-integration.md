## Approved product rules

- Only Admin signs in with email/password. Reception then shows all authorized identities; one employee card per person, with branch selection when needed. Paired phones show only the bound employee. No local/demo role or identifier establishes authority.
- Each employee entry requires the six-digit authentication PIN. A pairing code binds a device; it is not that PIN. Phone remembrance remains bounded by server expiry/revocation.
- Admin starts the reception base. Cerrar sesión inside ANY operating profile returns to selection and revokes only its employee operating token, retaining Admin base and phone proof. Cerrar sesión FROM the Admin-backed selector ends Admin and requires credentials. No extra Admin-card reauthentication prompt was approved.
- API mode never hydrates demo business persistence or falls back to local success. Only exact VITE_DEMO_MODE=true enables explicit demo entry; real principals use API mode. Rich-demo selects seed variety only. Unsupported business actions remain visibly unavailable/read-only.
- Personal retains its existing table/edit modal. Explicit server account/profile linking belongs in Edit Staff, with row PIN controls unchanged. Devices use the original styled DevicePairingModal, not the technical panel.
- NEW requested flow: select profile/branch, enter the Admin-issued temporary PIN ONCE, then open mandatory setup with that identity fixed and ONLY new PIN plus confirmation. No operating session before change; continue into the chosen profile only after server-confirmed change. Do not repeat identity or temporary-PIN input in the same flow.

## Daily P1 workflow

1. Admin signs in on the existing screen, approves the device if requested, clicks Verificar aprobación when pending, then chooses an identity. Employees enter with their own PIN.
2. Personal loads server branch/profile/account choices. Link an existing unlinked profile in Edit, then issue an initial PIN. Salary/shift/roster CRUD and unsupported P2-P6 business screens remain unavailable rather than local successes.
3. For a phone, Admin explicitly generates a code in the original device modal. The phone binds once, sees its own card and requires PIN. Close/reopen the modal to refresh its list; revoke is a separate confirmed action.
4. Profile Cerrar sesión returns to selection without unlinking or ending Admin base. Selector Cerrar sesión ends Admin; employee entry still requires PIN.
5. Enter the issued temporary PIN once on the selected employee card. The same dialog fixes that identity and requests only new PIN plus confirmation; save completes setup before operating entry. This is implemented and automated-tested; real-browser acceptance remains pending.

## Contract and implementation boundaries

- Add `rental_assets`, `rentals`, `rental_charges` (initial/renewal snapshots), `rental_cancellations` (including review metadata). Do not introduce a rental-rate versioning framework or notification queue.
- Proposed Payment extension: nullable `order_id` plus `rental_charge_id`, exactly-one-owner CHECK, retaining unique `order_id`. Reuse `PaymentReviewEvent` and existing terminal client; do not weaken legacy single-payment orders. Freeze exact migration after baseline investigation.
- Server prices, dates, actor identity, scope, allowed actions, idempotency and exclusivity are authoritative. Every lifecycle operation targets a rental identity, never just the currently selected asset.
- Cancellation record doubles as persistent admin alert; financial fields immutable, review acknowledgement idempotent. Reject stale preview if payment/debt/period facts changed.
- Cash/card/transfer receipts and mixed tender must reconcile without counting pending transfers again as separate shortfall. Existing membership access policy must not silently change because rental debt is added.
- Before any real card flow, persist a bound intent and fail closed when provider configuration is unavailable. No mock fallback in live rentals. Calls to providers are not performed while holding database locks. Real provider credentials/sessions require separate explicit authorization.
- Work directly in existing frontend modules and injected authenticated request transport. Only approved new UI: admin controls, cancellation confirmation, owner inventory launchers, rental alerts/review.
- Not included: future reservations, deposits, damage/late penalties, offline rentals, external notifications, universal member history, deployment or production data changes.
